# Salvus Incident Evidence — Security Architecture & AI Vision Readiness Guide

## Overview

In the Salvus emergency response system, citizen-uploaded photos serve as **situational evidence** ($1 \text{ Incident} \rightarrow 0..N \text{ Attachments}$).

This document outlines the security, privacy, and architectural policies governing evidence storage, authority inspection, and future multimodal AI vision analysis.

---

## 1. Core Trust Principle

> **"A citizen photo is an unverified field observation, not established ground truth."**

- **Honest Labeling**: All photos displayed in the Authority Command Center and Citizen status views are labeled with:
  `Citizen-provided photo · Unverified field observation`.
- **Decision Support Boundary**: Photographic evidence and future AI visual inferences are strictly **decision support**. Under no circumstances will image analysis autonomously dispatch responders, alter triage verification status, or close/resolve an incident without human coordinator authorization.

---

## 2. RBAC & Security Isolation Matrix

| Actor Role                            | Upload Permission                            | View / Read Permission                         | Delete Permission                                     |
| :------------------------------------ | :------------------------------------------- | :--------------------------------------------- | :---------------------------------------------------- |
| **Citizen (Reporter / Owner)**        | Can upload to **their own** active incident  | Can view attachments on **their own** incident | Can delete attachment within active reporting session |
| **Citizen (Unrelated / Third-party)** | ❌ Blocked (`403 Forbidden`)                 | ❌ Blocked (`403 Forbidden`)                   | ❌ Blocked (`403 Forbidden`)                          |
| **Assigned Responder**                | Can upload on-scene evidence photos          | Can view attachments for **assigned** incident | ❌ Blocked                                            |
| **Unassigned Responder**              | ❌ Blocked                                   | ❌ Blocked (`403 Forbidden`)                   | ❌ Blocked                                            |
| **Emergency Authority / Dispatcher**  | Can upload authoritative aerial/field photos | Can view all operational incident attachments  | Can delete spam / duplicate attachments               |

## 3. Privacy, PII & EXIF Policy

### A. PII Shielding in Evidence Lightbox

- **Strict Omission**: The Authority Evidence Lightbox (`EvidenceLightboxModal`) intentionally omits citizen phone numbers, private home addresses, medical details, and personal contact info from the evidence inspection view.
- **Operational Focus**: Only operational parameters (Ticket ID, incident category, incident coordinates, timestamp, and binary file attributes) are displayed.

### B. EXIF Metadata Policy

1. **Binary Chain-of-Custody**: The original uploaded image binary is cryptographically fingerprinted using **SHA-256** checksumming to maintain forensic integrity and prevent silent alteration.
2. **Location Privacy**: GPS metadata embedded within EXIF tags is not exposed to public consumers or third parties. Location is strictly tied to the verified incident report record.
3. **MIME & Magic Byte Verification**: Every upload is verified against genuine binary magic bytes (`\xff\xd8\xff` for JPEG, `\x89PNG\r\n\x1a\n` for PNG, `RIFF....WEBP` for WebP), eliminating file spoofing.

---

## 4. Real-time & WebSocket Performance

- **No Binary over Sockets**: Socket.IO events (`new_incident`, `incident_updated`) NEVER transmit binary payloads or base64 image data over WebSockets.
- **Lightweight Reference**: Socket payloads carry only lightweight attachment metadata (`id`, `url`, `thumbnail_url`, `size_bytes`, `original_filename`).
- **Progressive Delivery**:
  - The Authority Incident Inspector loads low-bandwidth **thumbnail derivatives** (`thumbnail_url`) generated by Cloudinary/S3.
  - The full-resolution image is requested on-demand only when the dispatcher opens the Evidence Lightbox viewer.

## 5. AI Vision Readiness Contract (`AIVisionAssessment`)

The backend establishes a normalized Pydantic contract for future multimodal vision models (e.g. Gemini 1.5 Pro / Flash) consuming secure backend storage references:

```python
class AIVisionAssessment(BaseModel):
    hazard_detected: bool = True
    hazard_type: str
    observations: list[AIVisionObservation] = []
    water_depth_estimate: str | None = None   # e.g., "0.5m - 1.0m (approx knee-depth)"
    damage_severity_hint: str | None = None   # e.g., "HIGH"
    confidence: float = 0.0                   # Normalized 0.0 - 1.0
    uncertainty_flags: list[str] = []         # e.g., ["LOW_LIGHT", "OCCLUSION"]
    analyzed_at: str | None = None
    model_version: str | None = None
    disclaimer: str = "AI ESTIMATE — UNVERIFIED DECISION SUPPORT ONLY"
```

### Invariants:

1. AI vision workers consume backend **`storage_key`** or authenticated streams; they do not expose public API keys to the frontend.
2. Every output payload includes the mandatory disclaimer: `AI ESTIMATE — UNVERIFIED DECISION SUPPORT ONLY`.
3. AI inferences are stored in a dedicated `vision_assessment` container and never overwrite the official incident severity or status without human approval.
